<section class="chapter" id="ch1">
<div class="kicker">Chapter One</div>
<h1>A note from the kitchen</h1>
<p class="standfirst">Why login systems stopped remembering you, and what they hand you instead.</p>
<hr class="rule">
<p class="first"><span class="dc">Y</span>ou are building Tiffintime, a small app that lets students pre-order lunch from the college canteen. Version one was simple: when someone logged in, the server wrote their user id into its own memory and handed back a session cookie. Every request after that carried the cookie, the server looked it up, and life was good.</p>
<p>Then came fest week. Orders tripled, one server started sweating, and you added a second behind a load balancer. Half the logins broke that afternoon. A request that began on server A would land on server B, which had never heard of the session, and students found themselves logged out somewhere between the dosa and the payment.</p>
<p>You could fix this with a shared session store, a Redis box both servers consult on every request. That works, and plenty of serious systems do exactly that. But every request now depends on one more moving part. The JWT approach flips the responsibility: instead of the server remembering who you are, it writes a signed note at login and hands it to you. You carry it. Any server that knows the signing key can verify the note on its own, no shared memory required.</p>
<p>That note is a JSON Web Token, and it is three pieces of text joined by dots.</p>

<div class="cap"><b>Figure 1.1</b> &nbsp;The three parts of a signed JWT</div></div>
<p>The header says which algorithm sealed the token. The payload carries <em>claims</em>, small statements the server vouches for: who you are (<code>sub</code>), who wrote the note (<code>iss</code>), when it stops being valid (<code>exp</code>). The signature is the seal itself: the server ran the first two parts through HMAC with its secret key, and any change to a single character breaks the match.</p>
<p>Here is the part that surprises everyone the first time. The payload is only Base64URL-encoded, not encrypted. Anyone holding the token can read every claim in it, so never put secrets inside one, and never paste a real token into a website to inspect it; decode locally or with a dummy token instead. What the signature gives you is integrity and authenticity of the writing. It says nothing about who is carrying it. A JWT is a <em>bearer</em> token, and that single fact drives most of this book. (An encrypted form, JWE, exists for contents that must be hidden; this book, like most login systems, uses the signed form.)</p>
<div class="dyk"><div class="bt">Did you know?</div>
<p>RFC 7519, the standard that defines the format, suggests pronouncing JWT like the English word &ldquo;jot&rdquo;. You will still hear &ldquo;jay-double-tee&rdquo; in most meetings.</p></div>

<section class="chapter" id="ch2">
<div class="kicker">Chapter Two</div>
<h1>The front door</h1>
<p class="standfirst">Passwords, hashing, and the handshake that ends with a token in hand.</p>
<hr class="rule">
<p class="first"><span class="dc">B</span>efore any token exists, someone has to prove who they are. For Tiffintime that is an email and a password, and your first real responsibility is deciding what happens to it. The honest answer: as little as possible. You never store the password. You store a <em>hash</em>, the output of a function that is easy to compute one way and hopeless to reverse, so a leaked database hands attackers hashes, not passwords.</p>
<pre><span class="k">const</span> bcrypt = <span class="f">require</span>(<span class="s">"bcrypt"</span>);

<span class="c">// signup: run once, store only the hash</span>
<span class="k">const</span> hash = <span class="k">await</span> bcrypt.<span class="f">hash</span>(password, <span class="s">12</span>);          <span class="n">1</span>
<span class="k">await</span> db.users.<span class="f">insert</span>({ email, password_hash: hash });

<span class="c">// login: fetch, then compare on your server</span>
<span class="k">const</span> row = <span class="k">await</span> db.users.<span class="f">findByEmail</span>(email);            <span class="n">2</span>
<span class="k">const</span> ok = row &amp;&amp; <span class="k">await</span> bcrypt.<span class="f">compare</span>(password, row.password_hash);
<span class="k">if</span> (!ok) <span class="k">return</span> res.<span class="f">status</span>(<span class="s">401</span>).<span class="f">json</span>({ error: <span class="s">"invalid credentials"</span> }); <span class="n">3</span></pre>
<div class="legend">
<p><span class="n">1</span> bcrypt is deliberately slow, which is what a guessing rig hates. 12 is its cost factor: each step up doubles the work. Tune it so one hash takes a comfortable fraction of a second.</p>
<p><span class="n">2</span> The comparison happens on your server. The database hands back the stored hash; it never sees the password and never decides anything.</p>
<p><span class="n">3</span> One error message for unknown email and wrong password alike. Never tell a stranger which half they got right.</p>
</div>
<p>Once the password checks out, the server signs an <strong>access token</strong> that lives for minutes and opens the API, and issues a longer-lived <strong>refresh credential</strong> for renewal. Chapter Ten makes the latter opaque.</p>

<section class="chapter" id="ch3">
<div class="kicker">Chapter Three</div>
<h1>The bouncer</h1>
<p class="standfirst">One middleware function, three questions, and the code behind them.</p>
<hr class="rule">
<p class="first"><span class="dc">A</span> week after launch, Tiffintime has routes worth protecting: <code>/api/orders</code>, <code>/api/profile</code>, <code>/api/wallet</code>. Each needs the same answer to the same question: who is asking, and is their note still good? In Express, a shared question becomes <em>middleware</em>, one function before every route handler. The numbered notes explain which parts the protocol fixes, which the library owns, and which are yours to shape.</p>
<pre><span class="k">const</span> jwt = <span class="f">require</span>(<span class="s">"jsonwebtoken"</span>);
<span class="k">if</span> (!process.env.JWT_SECRET) <span class="k">throw new</span> <span class="f">Error</span>(<span class="s">"misconfigured"</span>); <span class="n">1</span>
<span class="k">function</span> <span class="f">requireAuth</span>(req, res, next) {
  <span class="k">const</span> token = (req.headers.authorization || <span class="s">""</span>).<span class="f">replace</span>(<span class="s">"Bearer "</span>, <span class="s">""</span>); <span class="n">2</span>
  <span class="k">try</span> {
    <span class="k">const</span> p = jwt.<span class="f">verify</span>(token, process.env.JWT_SECRET, {
      algorithms: [<span class="s">"HS256"</span>],                          <span class="n">3</span>
      issuer: <span class="s">"api.tiffintime.app"</span>,                  <span class="n">4</span>
      audience: <span class="s">"tiffintime-api"</span>,
    });
    <span class="k">const</span> ok = p.use === <span class="s">"access"</span> &amp;&amp; <span class="k">typeof</span> p.sub === <span class="s">"string"</span> &amp;&amp; p.sub.length &gt; <span class="s">0</span> <span class="n">5</span>
      &amp;&amp; Number.<span class="f">isFinite</span>(p.exp) &amp;&amp; Number.<span class="f">isFinite</span>(p.iat)
      &amp;&amp; <span class="k">typeof</span> p.jti === <span class="s">"string"</span> &amp;&amp; p.jti.length &gt; <span class="s">0</span>;
    <span class="k">if</span> (!ok) <span class="k">throw new</span> <span class="f">Error</span>(<span class="s">"claims"</span>);
    req.user = p; <span class="f">next</span>();                           <span class="n">6</span>
  } <span class="k">catch</span> {
    res.<span class="f">status</span>(<span class="s">401</span>).<span class="f">json</span>({ error: <span class="s">"invalid_token"</span> });    <span class="n">7</span>

<div class="legend">
<p><span class="n">1</span> Your policy: the secret lives in the environment, never in code, and a missing one kills the app at boot. The variable name is yours.</p>
<p><span class="n">2</span> Teaching sketch: this string replacement does not enforce the Bearer scheme. Use the strict header parser in Chapter Seven when implementing the boundary.</p>
<p><span class="n">3</span> Protocol defense: pin the algorithm. Without the pin, jsonwebtoken v9 infers a family from your key type; the rules then change the day your keys do (Chapter Five).</p>
<p><span class="n">4</span> Library contract plus your values: <code>issuer</code> and <code>audience</code> are jsonwebtoken's option names; the strings are yours, set at login. Change one side and you must change both.</p>
<p><span class="n">5</span> Your claims policy: API-access tokens only, with a subject, an id, and sane times. RFC 7519 makes most claims optional; your profile decides which are required.</p>
<p><span class="n">6</span> Express convention: <code>req.user</code> is an ordinary property name; <code>req.account</code> works if your handlers agree.</p>
<p><span class="n">7</span> One answer for every failure: expired, forged, or missing, the caller sees the same 401 and learns nothing extra.</p>
</div>
<p>Two ideas weigh more than they look: <strong>authentication is not authorization</strong> (this function answers &ldquo;is the note valid&rdquo;; who may cancel which order comes later), and &ldquo;stateless&rdquo; is the signature check alone (revocation adds memory back, by choice).</p>

<div class="kicker">Chapter Four</div>
<h1>The borrowed key</h1>
<p class="standfirst">An incident: forty meals, one stolen token, and what a replay really costs.</p>
<hr class="rule">
<p class="first"><span class="dc">T</span>he ticket arrives on a Tuesday. Priya, a second-year, reports forty meals ordered on her account to a block across town, while she sat in class. Her password is unchanged. There are no reset emails and no failed-login alerts. Whoever did this did not break in. They walked in.</p>
<p>The trail, once you pull it, is short. Priya had posted a review on the canteen page. Beneath it sat a comment that was not a comment at all: another user had typed a script, and the page rendered it as written. When her browser drew that comment, the script ran with every right her own page had. It read her token from where the app kept it, posted a copy to a server far away, and vanished. From there the replay was trivial: attach the token to requests, and the bouncer nods.</p>

<div class="pq">The lock worked perfectly. The key was borrowed.</div>
<p>Sit with that for a moment, because it is the bearer model stating its price. Verification cannot tell Priya from a copy of her token; the damage lasts until the token expires or is revoked, scoped only by what the token was allowed to do.</p>
<p>The defenses come in layers, and honesty about each one matters. Storing the token in an <code>HttpOnly</code> cookie keeps it away from a script that reads the page, but a script running inside your origin can still send requests as Priya, and cookie transport now owes you CSRF defenses of its own. Short token lifetimes shrink the window, and revocation closes it early for tokens you know are bad; refresh rotation detects a stolen refresh token later, but it does nothing for an access token already issued. And the first fix is the boring, total one: render user content as text. That means output encoding for the context it lands in, safe DOM APIs instead of innerHTML, and sanitization when you must accept rich HTML. Everything else buys time.</p>

<h1>The forger</h1>
<p class="standfirst">The attacker who never steals anything, because he writes his own note.</p>
<hr class="rule">
<p class="first"><span class="dc">C</span>hapter Four's thief needed Priya. This attacker needs nobody. He writes a token himself, and his pen is the token's own header, which names the algorithm the server should use to check the seal.</p>
<p>Early verifiers trusted that name. Say <code>"alg": "none"</code> and a careless library would accept a token with no signature at all; the seal-shaped space at the end is simply empty. Say <code>"alg": "HS256"</code> to a server that expects RS256, and a library that obeys the header will feed the server's <em>public</em> key into HMAC as if it were the shared secret. A public key is public. The attacker signs with it, and the forged token verifies.</p>

<div class="cap"><b>Figure 5.1</b> &nbsp;Two forgeries, one lesson</div></div>
<div class="note"><div class="bt">Two different root causes</div>
<p><strong>Verifier confusion</strong> is the token choosing its own verification. The fix is configuration: the server pins the expected algorithm and the matching trusted key, HMAC secret or issuer public key.</p>
<p><strong>A weak secret</strong> is a different failure entirely. If the HMAC secret is a human word, attackers guess it offline against any captured token, at no cost to them. The fix is entropy: a generated 256-bit random secret. No verifier setting repairs a guessable key.</p></div>
<p>This is why Chapter Three's bouncer looked so stubborn. The pinned algorithm list, the pinned issuer, and the secret from the environment live on the server, where the token cannot reach them, and the claims checks behind them decide what the note is for and whether it is still fresh.</p>
<div class="dyk"><div class="bt">Did you know?</div>
<p>In 2022, PyJWT, shipped an algorithm-confusion flaw (CVE-2022-29217). A year later the fast-jwt library had one of its own (CVE-2023-48223). Mature libraries get this wrong, which is exactly why the defense is your configuration and timely updates, not blind trust in the package.</p></div>

<p>Keep three different mechanisms apart, because books and blogs love to blend them. <strong>Heuristic risk signals</strong>, the ones in the figure, are probabilistic. They can be spoofed, they drift when users travel or switch networks, and they are never an authenticator; they only tune how suspicious to be. <strong>Context binding</strong> ties the token to a second secret kept in a hardened cookie, with a hash of it inside the token, so the pair must arrive together. Its limits are concrete: steal both and replay still works, a script inside your origin rides the pairing, and the pattern is an illustrative one rather than a normative standard, so check current guidance before adopting it. <strong>Sender-constraining</strong>, through DPoP or mutual TLS, binds the token to a key the client must prove it holds on every request. The client proves possession on every request, so a copied token on its own replays nothing. The cost is real key management, and it still depends on correct validation and on the key staying protected.</p>
<p>And why not simply bind tokens to IP addresses? Because IPs lie politely. Campus NATs and mobile carriers move thousands of users through one address, while one user on a VPN changes address mid-session. Treat IP as one signal among several, never as identity.</p>
<div class="dyk"><div class="bt">Did you know?</div>
<p>The W3C publishes guidance on <em>limiting</em> browser fingerprinting, because the same signals that help you spot a thief can be used to track people across the web without their knowledge. Collect what your risk decisions need. Not everything you can reach.</p></div>
<p>Tiffintime now has a better question than "does this token verify?" The next chapters turn those boundaries into an implementation: storage, renewal, logout, current permissions, and incident drills.</p>

<section class="chapter" id="ch7"><div class="kicker">Chapter Seven</div><h1>Writing the note</h1><div class="standfirst">A small token profile, deliberate defaults, and code you can reason about.</div><hr class="rule"><p class="first"><span class="dc">B</span>y now, Tiffintime has learned that a signature is only one part of the contract. It needs a written agreement between the code that issues a token and the code that accepts it. Otherwise a change on Monday becomes an unexplained login failure on Tuesday.</p>
<p>Our application profile is deliberately small. It is not the OAuth JWT access-token profile from RFC 9068. We use a custom <code>use</code> claim to separate access tokens from other credentials, a string subject for the internal user ID, and an explicit issuer and audience. In a real OAuth deployment, use the authorization server's documented profile rather than inventing a parallel one.</p>
<table><tr><th>Field</th><th>Tiffintime's contract</th><th>Why it exists</th></tr>
<tr><td><code>alg</code></td><td>HS256, configured on both sides</td><td>The token does not choose its own verification rules.</td></tr>
<tr><td><code>iss</code> / <code>aud</code></td><td><code>api.tiffintime.app</code> / <code>tiffintime-api</code></td><td>Who issued it, and which API may accept it.</td></tr>
<tr><td><code>sub</code> / <code>use</code></td><td>Internal user ID / <code>access</code></td><td>Subject identity and this token's purpose.</td></tr>
<tr><td><code>iat</code> / <code>exp</code></td><td>Integer seconds, at most 900 apart</td><td>A chosen 15-minute lifetime, not a universal JWT rule.</td></tr>
<tr><td><code>jti</code></td><td>A fresh random identifier</td><td>A handle for audit and revocation policy, not replay protection by itself.</td></tr></table>
<h2>Issue only after authentication succeeds</h2>
<p>The password comparison from Chapter Two, account-status checks, rate limits and any required MFA run first. The function below has no password logic. Giving it a user ID means its caller already authenticated that user. Never fill that ID from an untrusted request body just because the function accepts a string.</p>
<pre>const jwt = require(&#x27;jsonwebtoken&#x27;);
const { randomUUID } = require(&#x27;node:crypto&#x27;);
const ISSUER = &#x27;api.tiffintime.app&#x27;;
const AUDIENCE = &#x27;tiffintime-api&#x27;;
const ACCESS_SECONDS = 900;
// secret comes from trusted server configuration, never the request.
function issueAccess(userId, secret) {
  if (typeof userId !== &#x27;string&#x27; || !userId) throw new Error(&#x27;subject&#x27;);
  return jwt.sign({ use: &#x27;access&#x27; }, secret, {
    algorithm: &#x27;HS256&#x27;, subject: userId, jwtid: randomUUID(),
    issuer: ISSUER, audience: AUDIENCE, expiresIn: ACCESS_SECONDS,
  });
}</pre>
<p><code>subject</code> and <code>jwtid</code> are jsonwebtoken option names. They become <code>sub</code> and <code>jti</code> in the payload. Rename the local <code>userId</code> variable if you like; do not rename an API option and expect the library to infer your intention. Put a claim in either the payload or its corresponding option, not both.</p>
<p>Use a signing secret generated from at least 32 cryptographically random bytes for HS256. A 32-character slogan does not have 256 bits of entropy. A length check can catch an empty configuration, but cannot prove randomness. Keep the key in server-side secret storage, separate between environments, and out of source control and logs. All services using HMAC to verify can also sign; Chapter Thirteen follows that consequence.</p>
<div class="dyk"><div class="bt">Did you know?</div><p>In jsonwebtoken, <code>expiresIn: 900</code> means 900 seconds. <code>expiresIn: "900"</code> means 900 milliseconds. In the checked version, the latter produces <code>exp - iat === 0</code> after conversion to whole seconds. <code>"15m"</code> is explicit and works as intended. Quotation marks can change a security policy.</p></div>
<h2>A stricter boundary than the first sketch</h2>
<p>Chapter Three used a short Express sketch to explain middleware. Its string replacement is not a complete Authorization-header parser. This version accepts exactly one compact signed JWT after the Bearer scheme. The scheme is case-insensitive; the claim strings are not. Rejecting extra spaces and trailing material is our strict parsing policy, not a new rule imposed on every JWT library.</p>
<pre>function verifyAccess(header, secret, now = Math.floor(Date.now() / 1000)) {
  const m = typeof header === &#x27;string&#x27;
    ? /^Bearer ([A-Za-z0-9_-]+\.[A-Za-z0-9_-]+\.[A-Za-z0-9_-]+)$/i.exec(header)
    : null;
  if (!m) throw new Error(&#x27;invalid_token&#x27;);
  const p = jwt.verify(m[1], secret, {
    algorithms: [&#x27;HS256&#x27;], issuer: ISSUER, audience: AUDIENCE,
    clockTimestamp: now, clockTolerance: 30,
  });
  if (!p || typeof p !== &#x27;object&#x27; || Array.isArray(p)
    || p.use !== &#x27;access&#x27; || typeof p.sub !== &#x27;string&#x27; || !p.sub
    || typeof p.jti !== &#x27;string&#x27; || !p.jti
    || !Number.isInteger(p.iat) || !Number.isInteger(p.exp)
    || p.iat &gt; now + 30 || p.exp &lt;= p.iat
    || p.exp - p.iat &gt; ACCESS_SECONDS) throw new Error(&#x27;invalid_token&#x27;);
  return p;
}</pre>
<p><code>jwt.verify</code> checks the signature, the allowed algorithm, issuer, audience, expiry and any present not-before claim. Our checks after it enforce the application's required shape and maximum lifetime. Registered claims are not all universally mandatory in RFC 7519; our profile makes these ones mandatory here.</p>
<p>The 30-second tolerance is a chosen deployment allowance for clock differences. It means a token may pass for up to that much longer around an expiry boundary. Keep machines synchronized and select the smallest tolerance you can support. Increasing it until tests stop failing is not clock management.</p>
<p>Wrap this function in middleware that converts failures to the same external 401 response. Keep detailed reasons in restricted, redacted telemetry. A successful return identifies the token's subject; it still does not authorize a wallet transfer or someone else's order.</p>

<p>For our same-origin app, a server-managed browser session is a reasonable starting point. A backend-for-frontend can hold downstream API tokens while the browser gets only a session cookie. It remains stateful; not every application needs this architecture.</p>
<p>If the browser must call an API directly, document why. Memory-only access tokens and protected renewal reduce persistence, not the privileges of hostile code in your origin. Memory is not an XSS defense.</p>
<h2 class="ch8page2">CSR and SSR do not settle authentication</h2>
<p>CSR assembles the UI in the browser; SSR assembles response HTML on the server. Neither grants permission: the server returning private data must validate credentials and access.</p>
<p>Never cache personalized SSR output under a shared anonymous key or treat a hidden CSR admin button as authorization. Both need private-response cache policy and server checks. Tokens in rendered HTML are exposed to page inspection and potentially scripts; SSR is no secret vault.</p>
<div class="dyk"><div class="bt">Did you know?</div><p><code>HttpOnly</code> blocks script reads, not authenticated requests. MDN notes that cookies still accompany JavaScript <code>fetch()</code>. A cookie flag does not end the XSS problem.</p></div>
<h2>Choose against the actual client</h2>
<p>Mobile apps have protected platform storage and different cookie/redirect behavior. Machine clients have different key ownership. Do not copy browser decisions into either.</p>
<p>The next examples use a same-origin browser/server, short-lived access tokens and server-tracked opaque refresh credentials. The lifecycle also applies to opaque browser sessions. Choose one coherent architecture, not every pattern at once.</p>

Sometimes you need both.</div><hr class="rule"><p class="first"><span class="dc">A</span>t lunch, Priya opens another site. That page submits a request to Tiffintime. Nothing about signing the cookie's contents prevents that.</p>
<p>This is the classic CSRF problem: an attacker causes an authenticated browser to make an unwanted request. A script-set Bearer header does not normally attach itself to an attacker's cross-site form, so that transport changes the classic threat. It does not fix XSS, which runs inside your own origin.</p>
<h2>A cookie with deliberate boundaries</h2>
<pre>Set-Cookie: __Host-refresh=&lt;opaque-random-value&gt;; Path=/;
            Secure; HttpOnly; SameSite=Strict; Max-Age=604800</pre>
<p>This is a header illustration, not a live credential. The line is shown wrapped for reading; a real Set-Cookie value is emitted as one header. The seven-day age is an example policy. The server must enforce expiry too. Deleting or expiring the browser cookie is not a substitute for invalidating its server-side record.</p>
<ul><li><code>Secure</code> limits normal transmission to HTTPS. It does not repair a compromised endpoint.</li><li><code>HttpOnly</code> blocks ordinary script reads. It does not stop an in-origin script using the session.</li><li><code>SameSite=Strict</code> is our same-site example. It may break legitimate cross-site entry or sign-in flows; choose and test the value your flow needs.</li><li>The <code>__Host-</code> prefix requires Secure, <code>Path=/</code>, and no Domain attribute on supporting browsers. Do not append <code>Domain=.tiffintime.app</code> and still claim that prefix's isolation.</li></ul>
<p>HTTP's <code>Max-Age</code> counts seconds. Framework APIs sometimes use different units. Check the API you actually call instead of copying the number between a raw header and an Express option.</p>
<h2>Give state-changing requests an explicit token</h2>
<p>For our server-tracked browser session, use a maintained framework's synchronizer-token support. The server generates an unpredictable CSRF value, binds it to the session, and exposes it to the legitimate page through a safe response. A state-changing request returns it in an explicit header or form field. The server compares it with the expected value before changing anything.</p>
<pre>// Illustrative client integration; the server must validate the token.
await fetch(&#x27;/api/orders&#x27;, {
  method: &#x27;POST&#x27;,
  credentials: &#x27;same-origin&#x27;,
  headers: {
    &#x27;Content-Type&#x27;: &#x27;application/json&#x27;,
    &#x27;X-CSRF-Token&#x27;: csrfTokenFromTrustedPage,
  },
  body: JSON.stringify({ mealId: selectedMealId }),
});</pre>
<p>The header name is an application contract, not magic syntax. Rename it on both client and server if you must. Sending the cookie alone proves nothing about user intent. Attaching a token only in JavaScript also proves nothing unless the receiving server rejects missing and invalid values.</p>
<p>Keep token attachment limited to known application endpoints. A generic helper that forwards credentials or CSRF tokens to an arbitrary URL can leak them to an attacker-controlled destination. CORS determines which cross-origin responses a browser may expose; it is not an authorization system and does not replace the CSRF check.</p>
<p>For a stateless CSRF design, study the signed double-submit pattern bound to a changing session-specific value. Comparing a readable cookie with a matching request field without that binding is the naive variant, which OWASP discourages. SameSite, exact Origin checking and Fetch Metadata can be additional layers. Keep a defined fallback for clients that omit metadata.</p>
<h2>Login CSRF is a different surprise</h2>
<p>An attacker can try to log the victim into the attacker's account. The victim may then enter private information or perform actions in the wrong account. Protect login initiation and session transitions too; do not assume "not logged in yet" means there is no CSRF problem. In OAuth/OIDC, use the library's transaction binding, PKCE, state and nonce handling as applicable, rather than bolting a home-made redirect flow onto this local-login example.</p>
<h2>Fix the original XSS bug</h2>
<p>Use context-appropriate output encoding. Use safe text APIs for plain text. If rich HTML is a real product requirement, sanitize it with a maintained sanitizer and an explicit policy. Content Security Policy is a useful additional boundary, not permission to interpolate untrusted HTML. A CSRF token cannot protect you from code that already runs in your origin and can read that token.</p>

Asking for her password every fifteen minutes would make the app miserable. Issuing an access token that lives for months would make a stolen token miserable for everyone else. A refresh credential separates those lifetimes.</p>
<p>The refresh credential goes only to the renewal endpoint. It is not an API access token and should not authorize orders. It may be opaque; it does not need to be a JWT. Our example uses 32 random bytes, delivers the raw value to the client, and stores its SHA-256 digest with the session family.</p>
<pre>const { randomBytes, createHash } = require(&#x27;node:crypto&#x27;);
function newRefresh() {
  const raw = randomBytes(32).toString(&#x27;base64url&#x27;);
  const hash = createHash(&#x27;sha256&#x27;).update(raw).digest(&#x27;hex&#x27;);
  return { raw, hash };
}</pre>
<p>A fast hash is suitable here because the input is already high-entropy random data. That does not make SHA-256 suitable for human passwords. Passwords need a password-hashing scheme and work factor because humans do not choose 256 random bits. The two uses start from different threats.</p>
<p>Store the user ID, family ID, creation time, absolute expiry, used time, replacement relationship and revocation state beside that digest. Store only the minimum metadata needed for security and support. A leaked read-only token table should not immediately reveal raw bearer credentials.</p>

<h2>Absolute and idle expiry are separate</h2>
<p>An idle timeout ends a session that has not been used for a chosen interval. An absolute timeout ends it even if it is busy. Rotating the credential must not accidentally restart an unlimited absolute lifetime. Pick both against the sensitivity of the product and document whether renewal extends either.</p>
<p>A refresh response must not be cached as public content. Redact credentials from application logs, proxy logs, traces, error reports and analytics. A perfectly implemented one-time exchange is undone if the new credential goes into a debugging dashboard.</p>
<p>Finally, remember the limit: revoking R2 stops future renewal. An access token already issued may still work until expiry unless the API enforces a separate revocation or session-status check. Rotation and immediate access-token invalidation are different controls.</p>

Both send R1 after access expiry. Without serialization, both can read "unused" and create different replacements: one credential has become two live branches.</p>
<p>A single-flight promise coalesces one page's renewals, not other tabs, processes or attackers; enforce the invariant in the database.</p>
<h2>The invariant</h2>
<p>Consume each refresh credential at most once per family, serializing the check and the replacement write. A relational design locks the family row, then reads and updates its credential in one transaction; rotation and revocation share that lock.</p>
<pre>// Transaction outline, NOT a database-driver implementation.
BEGIN
  lock family row for this credential
  load credential by its hash under that family
  if family revoked or credential expired: reject
  if credential already used:
      mark family revoked
      COMMIT                       // persist the safety decision
      return reauthentication_required
  mark credential used
  insert replacement credential with the same absolute family expiry
COMMIT
return new credential and access token</pre>
<p>Commit reuse revocation before returning an HTTP error; an exception that rolls back the transaction would undo the safety decision. Transaction control is part of the security algorithm.</p>
<p>Keep locks short: pre-generate randomness, and never wait inside the transaction on network calls, remote signing or the client. A lost response does not undo a committed exchange.</p>
<h2>Lost responses force a policy decision</h2>
<p>If R1 → R2 commits but the response disappears, the client retries R1 and triggers reuse. Strict policy resets the session; bounded grace or idempotency reduces disruption. Reaccepting recent old tokens weakens the one-time rule.</p>
<p>Returning the same R2 on retry needs a reproducible or securely retained response; R2's hash cannot recover the raw value. An encrypted response cache holds credentials, with its own key, access controls and retention.</p>
<div class="client-actions"><h2>What should the client do?</h2>
<ul><li>Coalesce page renewals; coordinate tabs where supported without persisting secrets for coordination.</li><li>Retry once at most after successful renewal, only when replay semantics permit it.</li><li>Never blindly replay timed-out payment/order POSTs; use supported idempotency keys.</li><li>On terminal renewal failure, clear local auth state and offer sign-in; stop 401/refresh loops.</li></ul>
<p>Test with real database transactions, locks and isolation before deployment; a memory model cannot establish deployment behavior. The executed JWT tests do not test this transaction.</p>

<h2>A practical logout sequence</h2>
<p>Protect logout against unwanted state changes using the same CSRF policy as other cookie-authenticated actions. Find the authenticated family, persist its revocation, clear the matching browser cookie with the same name and relevant scope, and clear any in-memory access token. Deleting a cookie with a different path may leave the real credential in place.</p>
<p>Choose an idempotent response: logging out twice should not become a confusing error. If the revocation store is unavailable, the browser can discard its copy, but server invalidation remains unconfirmed. Report that partial result honestly.</p>
<h2>Staleness is a security policy</h2>
<p>A 60-second status cache can accept a just-revoked session during that window, plus propagation effects. Document the longest accepted stale interval across APIs, caches and replicas.</p>
<p>Sensitive actions need a fresh server-side decision and appropriate reauthentication. A menu read has different stakes. Define fail-open/fail-closed behavior per operation; do not inherit it accidentally from exception handling.</p>
<h2>When a signing key leaks</h2>
<p>One stolen access token suggests revoking a token or session. A stolen signing key means the attacker may mint arbitrary tokens that satisfy your normal checks. Retire the affected key, stop accepting it, investigate exposure, and reset affected sessions according to the incident plan. Waiting fifteen minutes is not enough if the attacker can keep creating tokens with fresh expiries.</p>
<p>A denylist can be smaller and shorter-lived than a full session store, but validation on that path is no longer zero-state. A plain server session may be simpler.</p>

<p>Asymmetric signatures change that distribution problem. The issuer holds the private signing key. Resource servers receive the public verification key. They can check the issuer's signature without gaining its signing power. That is a reason to choose RS256 or another supported asymmetric algorithm; it is not a claim that every asymmetric deployment is safer than every HMAC deployment.</p>
<h2>Resolve keys through established trust</h2>
<p>A token may contain <code>kid</code>, a key identifier. It is a selector, not proof that a key is trusted. Resolve it only inside the key set you have already associated with the configured issuer. An arbitrary filesystem path, SQL fragment or URL is not an acceptable interpretation of that string.</p>
<p>Likewise, do not blindly download a key from a token-supplied <code>jku</code> or <code>x5u</code>. Besides letting an attacker name their own trust anchor, uncontrolled fetching can become SSRF. Use preconfigured issuer metadata and JWKS destinations, outbound network limits, size/time limits and a maintained verifier. In a multi-issuer system, an unverified issuer can route to an allowlisted configuration; it cannot establish a new trust relationship.</p>

<h2>Rollover without breaking everyone</h2>
<ol><li>Generate the next key under the key-management policy. Make its public verification material available to verifiers.</li><li>After propagation, start issuing with the new key ID. Continue accepting the old key for already-issued tokens during a bounded overlap.</li><li>Observe adoption and errors. Account for maximum accepted lifetime, clock tolerance, JWKS caches and any other token classes using the old key.</li><li>Retire the old key when those credentials should no longer be accepted. A key compromise follows the emergency path, not a graceful overlap that keeps the compromised key trusted.</li></ol>
<p>Do not re-fetch JWKS on every unknown random key ID. An attacker can turn that into outbound traffic and denial of service. Bound refresh frequency, cache known keys according to policy, and define what happens when a needed key cannot be obtained.</p>
<h2>Keep algorithm and purpose boundaries together</h2>
<p>Bind a key to its expected algorithm. Avoid permissive "all algorithms we know" verification settings and compatibility switches that permit invalid key types. A correctly signed token from the wrong issuer, audience or purpose is still the wrong token.</p>
<p>An ID token tells an OAuth/OIDC client about authentication. An access token authorizes access to its intended resource under a profile. A refresh token is a renewal credential. Their names are not interchangeable because the payloads happen to look similar. Explicit typing and separate validation rules help prevent cross-JWT confusion.</p>
<div class="dyk"><div class="bt">Did you know?</div><p>The OAuth JWT access-token profile in RFC 9068 uses <code>typ: at+jwt</code> and defines required claims. The generic JWT RFC does not impose that same complete profile on every token. Standards compose; they do not collapse into one universal payload template.</p></div>
<p>JWT is also not the whole sign-in protocol. If Tiffintime later adds an external identity provider, use maintained OAuth/OIDC libraries and the provider's documented authorization-code flow with PKCE where required. Redirect validation, transaction binding and token validation remain separate jobs. Do not treat a decoded ID token as a complete login integration.</p>

<h2>Roles become stale</h2>
<p>A token with <code>role: admin</code> records issuance-time state; a database change does not edit it. When immediate removal matters, enforce current permission state or a revocation check; otherwise document the staleness bound.</p>

<h2>Fresh authentication is its own requirement</h2>

The team opens the JWT verifier, but most requests never got a token. The attack is against the password form. Changing the signing algorithm will not help.</p>
<p>Credential stuffing replays username/password pairs stolen from another service. Password spraying tries a small set of common passwords across many accounts. A brute-force run against one account has a different shape again. If you detect only "five failures on this account from this IP", a distributed campaign can stay below that rule.</p>
<h2>Observe several dimensions</h2>
<table><tr><th>Observation</th><th>Possible reading</th><th>Do not conclude</th></tr>
<tr><td>Many accounts fail from a source/network</td><td>Spraying, automation, or a shared network with broken clients.</td><td>That every user behind the NAT is malicious.</td></tr>
<tr><td>One account sees many sources</td><td>Distributed guessing or stuffing against that account.</td><td>That per-IP throttling alone will contain it.</td></tr>
<tr><td>Valid password, new environment, sensitive action</td><td>Enough risk to require stronger assurance.</td><td>That a password match proves the presenter is the owner.</td></tr>
<tr><td>Same fingerprint as before</td><td>One signal did not change.</td><td>That MFA, recovery checks or authorization can be skipped.</td></tr></table>
<p>Use rate limits across appropriate account and source dimensions, risk-triggered challenges, breached-password screening at password creation/reset, and MFA suitable for the threat. Aggressive lockouts can also become an account-denial-of-service tool. Test the attacker who deliberately locks a victim out.</p>
<p>Do not log submitted passwords to recognize spraying patterns. Log event outcomes and carefully selected metadata instead. A security dashboard should not become a second password database. Apply access control and retention limits to fingerprints, IP history and account-recovery records.</p>
<h2>Password hashes are not login credentials</h2>
<p>The server stores a salted password hash and compares a submitted password using the password-hashing library. If the server accepts the stored hash itself as a reusable login credential, the hash has become a password-equivalent bearer secret. That is not a benefit of hashing; it is a different, unsafe protocol.</p>
<p>A salt prevents identical passwords from producing identical stored results across separately salted records and frustrates precomputed lookup tables. It does not make a weak password strong or stop online guessing. A work factor increases the cost of testing a guess. It does not give you permission to leak the password database.</p>
<p>Chapter Two uses bcrypt to make the comparison easy to follow, not as a new-system recommendation. OWASP prefers Argon2id for new password storage, with scrypt as an alternative where Argon2id is unavailable. For existing bcrypt systems, benchmark the work factor and handle the implementation's input limit, commonly 72 bytes. Bytes are not characters; silently truncating a long Unicode password is a bad contract. Use a maintained password library and a planned migration rather than inventing a pre-hash workaround.</p>
<h2>HTTPS is not password hashing</h2>
<p>TLS protects data in transit between authenticated endpoints. Password hashing reduces the usefulness of a stolen password database. JWT signing protects integrity and issuer authenticity under a key. These controls protect different boundaries; none replaces the others. Also protect the hops behind a TLS-terminating proxy and ensure logs do not capture request bodies or Authorization headers.</p>
<div class="dyk"><div class="bt">Did you know?</div><p>NIST SP 800-63B-4 emphasizes blocking commonly used or compromised passwords and rate limiting. Forcing a new password every arbitrary interval is not the general answer. Require changes when compromise is suspected or established and follow the applicable assurance policy.</p></div>
<h2>Recovery is another front door</h2>
<p>A perfect login flow is irrelevant if password reset trusts a guessed security question or an attacker-controlled email change. Recovery tokens need unpredictability, narrow purpose, short validity and server-enforced one-time use. Revoke or re-evaluate existing sessions after a recovery event according to a documented policy.</p>
<p>Do not put a reset token through the normal access-token middleware. Separate audience or purpose rules keep it from becoming an accidental API credential. A notification about a recovery event should help the user respond, without exposing tokens or providing an easy phishing template.</p>

Decide which trust boundary failed, what you would check first, and what your proposed fix would still leave exposed. These are hypothetical teaching incidents. None is a claim about a real user, measured system or production breach.</p>
<h2>Case 1. The password is right. The city is wrong.</h2>
<p><strong>Question.</strong> A correct password arrives from a hosting-provider network after years of normal campus logins. Its browser fingerprint matches a prior login. Should the server issue a session?</p>
<p><strong>Worked answer.</strong> A matching fingerprint is not a factor. Attributes can be copied or spoofed, and a legitimate user may be on a VPN. Combine the signals under a risk policy and require an appropriate additional factor before a sensitive session or action. Check for stuffing across accounts and related recovery events. Do not silently trust the fingerprint or permanently block everyone using that network.</p>
<p><strong>What remains.</strong> A phishable factor can still be relayed, recovery can be weak, and an attacker may already hold a session. Where suitable, prefer stronger phishing-resistant authentication. Preserve an accessible, abuse-resistant recovery path.</p>
<h2>Case 2. No strange login, but the lunch wallet is empty.</h2>
<p><strong>Question.</strong> Priya reports unauthorized orders. There is no new password login. The token's signature, issuer and audience all check out. The request now comes from another network.</p>
<p><strong>Worked answer.</strong> Token replay does not require a new login. Investigate browser injection, credential exposure in logs and client-side storage, and the affected session timeline. Revoke the affected family and enforce access-token invalidation if the API supports it. Patch the XSS or leakage path; merely resetting her password may leave a copied access token working.</p>
<p><strong>What remains.</strong> A network change is a lead, not proof. In-origin malicious code can make requests from the victim's real browser and network, defeating a simple "new IP" alert. An HttpOnly cookie limits direct reading but not session riding.</p>
<h2>Case 3. Two refreshes, one credential.</h2>
<p><strong>Question.</strong> The same refresh credential appears twice in 200 milliseconds. One response was lost. Is this definitely theft?</p>
<p><strong>Worked answer.</strong> No. It might be theft, a tab race or a retry after a committed response disappeared. The server cannot identify the legitimate presenter from a bearer value alone. Apply the documented reuse policy, persist any family revocation, force reauthentication when required, and review metadata privately. Do not bypass the one-time invariant just because the interval is short.</p>
<p><strong>What remains.</strong> A strict policy may reset an innocent user's session. A retry-tolerant policy adds state and may expand the replay opportunity. Explain the tradeoff to the product team instead of pretending the database can infer intent.</p>
<h2>Case 4. New tokens appear, but the issuer never logged them.</h2>
<p><strong>Question.</strong> The attacker can create valid admin claims offline. Login logs are quiet. Would rate limiting stop them?</p>
<p><strong>Worked answer.</strong> Not if the signing secret was guessed offline or stolen. Contain the key exposure, retire the affected key, review issuance and verification trust, and reset the affected sessions according to policy. A long human phrase used directly as an HS256 key may be easier to guess than its byte length suggests. A public-key verifier configured incorrectly has a different failure: algorithm/key confusion.</p>
<p><strong>What remains.</strong> Algorithm pinning does not restore entropy to a weak secret. A strong secret does not correct an audience-confusion bug. Diagnose the mechanism before choosing the fix.</p>
<h2>Case 5. A legitimate token from the wrong service.</h2>
<p><strong>Question.</strong> A delivery-service token is accepted by the wallet API. Its signature verifies with a trusted issuer key. Is that enough?</p>
<p><strong>Worked answer.</strong> No. Verify intended audience, token purpose/type and applicable claims, then authorize the operation. Keep issuer-to-key relationships explicit. A key trusted for one issuer cannot become a universal cross-issuer trust anchor just because the key ID matches.</p>
<p><strong>What remains.</strong> Even the correct wallet token does not authorize another user's wallet. Object-level authorization remains a separate gate.</p>
<h2>Case 6. Can we bind the token to a fingerprint?</h2>
<p><strong>Question.</strong> The team suggests hashing the user agent and placing it inside the JWT. Would that stop off-device replay?</p>
<p><strong>Worked answer.</strong> An attacker who can copy the header can copy the input to that hash. Hashing a public or reproducible attribute does not turn it into a secret. Fingerprinting remains a risk signal, useful for anomaly scoring but not proof of possession.</p>
<p>A different, illustrative context-binding pattern uses a high-entropy secret in a hardened cookie and only its hash in the token. A token alone then fails the additional context check. Do not confuse that with a device fingerprint or a normative JWT requirement. Theft of both values still permits replay, and code in the original page can ride the live session. Evaluate current platform guidance before adopting it.</p>
<p>DPoP and mTLS instead bind a token to key possession. For DPoP, resource validation includes the proof's signature, expected key binding, HTTP method and target URI, issuance time, proof identifier and access-token hash as required. Add proof-replay handling and nonce processing where applicable. Hand this to a maintained protocol implementation, not a home-made "sign the token again" header.</p>
<p><strong>What remains.</strong> If hostile code can invoke the private key in the legitimate environment, it may produce valid proofs without extracting the key. A non-extractable browser key is not automatically an XSS boundary. mTLS also requires compatible TLS termination and certificate operations. Neither mechanism replaces authorization or lifecycle controls.</p>
<h2>Case 7. The user walks between mobile towers.</h2>
<p><strong>Question.</strong> A token was issued on one IP and used a minute later on another. Should every request be rejected?</p>
<p><strong>Worked answer.</strong> Not on that fact alone. Mobile carriers, VPNs and shared gateways can change or share apparent addresses. Use IP as one signal with uncertainty, and step up when the combined risk and action sensitivity justify it. A thief on the same NAT might keep the same IP, so exact IP equality can create both false rejection and false confidence.</p>
<p><strong>What remains.</strong> Fingerprinting and location history can become tracking. Minimize collection, restrict retention and access, and give the product a defensible privacy policy. Collecting every available attribute is not the same as building a useful detector.</p>

<h2>What was actually executed for this book</h2>
<p>The Chapter Seven issue/verify functions, opaque refresh generator, and a small owner-check predicate were exercised on Node.js 22.23.5 with jsonwebtoken 9.0.3. Thirty local assertions passed. The set includes valid and mixed-case Bearer headers, algorithm/issuer/audience/key mismatches, expiry/not-before boundaries, missing required claims, purpose, lifetime, future issue time, malformed headers, refresh digest shape, owner denial and the three duration variants.</p>
<p>Separately, the Chapter Three middleware sketch passed nine smoke checks, including a missing-secret boot failure. Default-algorithm behavior was checked on the named library version. These are local teaching checks, not penetration-test results or proof that the entire application is secure.</p>
<pre>// Deterministic expiry test idea, using the Chapter Seven function:
const now = Math.floor(Date.now() / 1000);
verifyAccess(&#x27;Bearer &#x27; + token, secret, now);       // present time
// Advance the verifier&#x27;s clock beyond expiry + configured tolerance.
assert.throws(() =&gt; verifyAccess(&#x27;Bearer &#x27; + token, secret, now + 931));</pre>
<p>The database transaction outline, HTTP/cookie integration, CSRF library integration, proxy settings, multi-tab behavior and deployment architecture were not executed as an end-to-end server for this book. They require integration tests in the actual application. Do not convert a written outline into a claim of production hardening.</p>
<h2>Keep failures useful without leaking credentials</h2>
<p>Record event time, request correlation, route, outcome category, relevant issuer/key version and a controlled account/session reference when appropriate. Exclude Authorization values, raw refresh credentials, cookies, passwords and reset links. Hashing a predictable user ID does not necessarily anonymize it. Give security logs an access policy and a retention limit.</p>
<p>Use distinguishable internal reasons such as bad audience, expired token, revoked family and permission denied. Present only what the client needs externally. A generic login message should not be paired with a timing difference that reliably reveals whether the email exists. Use maintained framework and password-authentication patterns rather than improvising dummy work on each route.</p>
<h2>The release review</h2>
<ul><li>Keys: generated securely, isolated per environment and purpose, no secrets in the repository, rotation rehearsed.</li><li>Validation: explicit algorithms, issuer, audience, purpose and profile; no decode-only authentication or permissive compatibility switches.</li><li>Transport: HTTPS and trusted proxy configuration; no tokens in URLs; no credential-bearing responses in shared caches.</li><li>Browser: cookie attributes tested, CSRF enforced on relevant actions, XSS defenses checked, credentials sent only to intended destinations.</li><li>Lifecycle: atomic rotation, absolute/idle expiry, reuse and retry behavior, logout and recovery effects, outage policy.</li><li>Permissions: ownership, tenant boundaries, sensitive-action reauthentication and immediate-role-change requirements tested.</li><li>Operations: redacted logs, alert thresholds, incident contacts, rollback and emergency key retirement exercised.</li></ul>
<p>A useful checklist can stop a release. If every line always receives a tick, it is decoration. Record the missing evidence, who owns it, and what would make the release acceptable.</p>

The promise to the user is the system.</div><hr class="rule"><p class="first"><span class="dc">A</span>t the end of the semester, Tiffintime is still a lunch app. It needs reliable sign-in, private orders, sensible recovery and a way to end a session. It does not get points for using every acronym in this book.</p>
<p>A server-side session with a random identifier is often the simpler choice for one first-party browser application that needs immediate logout and current permissions. A JWT can be useful when several services need to verify an issuer's statements locally, or when a standardized token profile is part of an existing protocol. Both designs still need secure login, transport, authorization and operations.</p>
<table><tr><th>Your real requirement</th><th>Start the design discussion here</th></tr>
<tr><td>Single browser app, server available on every request</td><td>Opaque server session, secure cookie and CSRF policy.</td></tr>
<tr><td>Several APIs verify one issuer without calling it on each request</td><td>Audience-restricted, short-lived tokens with explicit validation and key distribution.</td></tr>
<tr><td>Immediate global logout or permission removal</td><td>A live revocation/status decision; define cache and outage behavior.</td></tr>
<tr><td>Browser calls external OAuth APIs</td><td>Consider a backend-for-frontend; otherwise use the provider's supported browser-client flow.</td></tr>
<tr><td>Copied tokens must fail off-device</td><td>Evaluate sender constraints and key protection, not a user-agent hash.</td></tr></table>
<h2>The compact mental model</h2>
<p><strong>Authentication:</strong> how did the system establish a subject? <strong>Token validation:</strong> is this credential authentic and acceptable under our profile? <strong>Authorization:</strong> may that subject do this action to this object now? <strong>Session lifecycle:</strong> how does that permission-bearing relationship renew and end? A bug hides wherever two of those questions are mistaken for one.</p>
<p>A password hash is not encryption. TLS is not database protection. Base64URL is not confidentiality. A signature is not proof of who currently holds a bearer token. A token ID is not a replay detector until something tracks it. A fingerprint is not a person. And a successful local test is not a production security guarantee.</p>
<h2 class="gloss-title" id="glossary">Reference: a small glossary</h2>
<table><tr><th>Term</th><th>Meaning in this book</th></tr>
<tr><td>JWT / JWS / JWE</td><td>A claims-token format; its signed/MAC-protected form; its encrypted form. This book mostly uses compact signed tokens.</td></tr>
<tr><td>Bearer credential</td><td>Possession is sufficient for presentation, subject to the server's validation and policy. No separate presenter-key proof is inherent.</td></tr>
<tr><td>Issuer / audience / subject</td><td>Who issued a token, who should accept it, and whom its claims concern.</td></tr>
<tr><td>Refresh family</td><td>The server-tracked lineage of renewal credentials descended from one session grant.</td></tr>
<tr><td>JWKS / kid</td><td>A set of JSON Web Keys / a selector used within trusted key material.</td></tr>
<tr><td>BFF</td><td>A backend serving the browser that can hold upstream tokens while the browser uses a session cookie.</td></tr>
<tr><td>CSRF / XSS</td><td>Unwanted authenticated requests caused from another context / malicious code executing in the application's origin.</td></tr>
<tr><td>DPoP / mTLS</td><td>Application-layer proof-of-possession / mutual TLS mechanisms that can sender-constrain tokens.</td></tr></table>
<p>Return to Priya's stolen token one last time. The signature was fine. The system failed because it trusted possession too broadly and let code cross a boundary it should not have crossed. Good authentication design is the work of making those boundaries explicit, then testing the promises on both sides.</p>
